# DOCX из завершённого языкового этапа

## Предварительный DOCX во время окончательной сверки источника

Для постраничных двуязычных JSON `build_bilingual_checkpoint` может применить
те же `reader_options` и `reader_projection` к рабочему русскому тексту.
Сначала создаётся новый каталог подготовки:

```powershell
python -m kb_creator.scripts.build_bilingual_checkpoint --prepare --pages <pages-dir> --asset-root <assets-root> --source-pdf <source.pdf> --output <new-prepared-dir>
```

`PRELIMINARY_RU.md` содержит точный скомпилированный текст, включая все маркеры
`source-page-*`. `PRELIMINARY_RU_PROJECTION.json` содержит блоки с ID
`prelim-unit-00001` и точными `ru_sha256`; массив `separators` сохраняет
пробелы и пустые строки между ними. `PREPARE.json` связывает хеши всех JSON
страниц, PDF, текста, проекции и исходных ассетов. Шаблон
`reader_options.template.json` уже запечатан, но имеет `source_toc.state:
unresolved`. После просмотра источника автор решений заполняет существующую
форму `reader_options` и пересчитывает `options_sha256` по каноническому JSON.
Имена привязок здесь `PRELIMINARY_RU.md` и
`PRELIMINARY_RU_PROJECTION.json`; ID предварительные и не переносятся в
окончательную языковую проекцию без отдельной проверки.

```powershell
python -m kb_creator.scripts.build_bilingual_checkpoint --pages <pages-dir> --asset-root <assets-root> --config <docx_config.json> --output <new-docx-dir> --prepared <prepared-dir> --reader-options <sealed-reader-options.json> --source-pdf <source.pdf>
```

Сборка проверяет точные входы и исполнение решений в OOXML. Оглавление со
статусом `unresolved` блокирует сборку; обнаруженное исходное оглавление
нельзя объявить отсутствующим. `CHECKPOINT.json` сохраняет `accepted: false` и
`release_ready: false`. Такой DOCX остаётся предварительным; окончательная
цепочка начинается ниже с проверенного языкового результата.

Маршрут продолжает `language_complete`, полученный командой
`kb_creator.scripts.continue_language`. Он проверяет всю цепочку исходных
артефактов и использует существующий общий сборщик DOCX.

```powershell
python -m kb_creator.scripts.continue_docx build --language-root <language-final> --reader-options <reader_options.json> --config <docx_config.json> --title <title> --output <new-docx-attempt>
python -m kb_creator.scripts.continue_docx verify --root <new-docx-attempt>
```

Для языкового successor можно перенести прежние решения оформления общей командой:

```powershell
python -m kb_creator.scripts.rebind_reader_options --prior-result <old-language-final/result> --result <new-language-final/result> --options <old-reader_options.json> --output <new-reader-options-directory>
```

Она проверяет оба языковых результата, английский источник, порядок исходных
единиц и ассеты. Каждая используемая ссылка на русский блок должна сохранять
точный хеш. Если затронутый текст изменился, требуется новое решение оформления.
Новые options и отчёт создаются отдельно; копируются только выбранные замены
ассетов. Конфиг типографики передаётся сборщику отдельно. Перенос не означает
визуального принятия новой сборки.

Без `--runtime <runtime.json>` результат имеет состояние `pending_render`.
Он содержит `package/docx/document.docx` и `text-review-task.json`; передать
его как полностью проверенную книгу нельзя. Runtime задаёт существующие
`tools_root`, `pdftoppm`, `libreoffice`, `python`. Повторная сборка с runtime
использует новый каталог. Тяжёлые OCR и рендер в ночной очереди идут по одному.

После рендера создаётся `visual-review-task.json` с точным упорядоченным
набором страниц и хешами PNG. Только эти страницы входят в визуальную
проверку; PNG внутри ассетов не подменяют страницы рендера.

Агент читает весь фактический текст DOCX и смотрит каждую страницу. Ответы
хранятся вне каталогов неизменяемой сборки. Текстовый ответ использует схему
`kb_creator.docx_text_review_submission.v1` и точные `task_sha256`, `docx`,
`blocks` из задания; каждая строка содержит `block_id`, `text_sha256`, `read`.
Визуальный ответ использует `kb_creator.docx_visual_review_submission.v1`,
точные `task_sha256`, `docx`, `pages` из задания; к каждой странице добавляется
`read: true` только после фактического просмотра. Оба ответа требуют
`reviewer_role: agent` и `findings`. Неразрешённые текстовые замечания и любые
визуальные замечания запрещают завершение. Исправления оформляются новым
набором входных данных и новой сборкой с повторной проверкой.

```powershell
python -m kb_creator.scripts.continue_docx review --root <docx-attempt> --text-submission <text.json> --visual-submission <visual.json> --output <new-review-result>
python -m kb_creator.scripts.continue_docx verify --root <new-review-result>
```

Полный корректный ответ даёт `ready_for_independent_release`. Это ещё не
независимый release review, переносимый полный пакет или принятие книги
пользователем. Рабочая цепочка сохраняет привязки к исходному языковому запуску;
переносимость обеспечивается последующим пакетированием.

Известное ограничение существующего сборщика: книга без заголовков и пустое
содержание пока приводят к ошибке таблицы TOC (TD27). Маршрут не добавляет
вымышленные заголовки и не скрывает эту ошибку.

## Таблицы без шапки и внутренние заголовочные строки

В `reader_options.display_roles` решение `table_presentation` привязывает
оформление к точному `unit_id` и `ru_sha256`. Дополнительные поля:

- `suppress_empty_transport_header`: удалить первую служебную строку Markdown,
  только если она полностью пуста и не содержит элементов или закладок;
- `source_header_rows`: номера заголовочных строк, начиная с 1, **после** удаления
  служебной строки; пустой список означает таблицу без шапки;
- `source_evidence` и `reason`: основание принятого решения по исходнику.

Все поля обязательны. Решение меняет внутренний HTML и оформление DOCX,
сохраняя MASTER_RU и содержимое оставшихся ячеек. Непустая первая строка никогда
не удаляется этим механизмом. Обычные таблицы без такого решения используют
прежнее оформление. Проверка решения не заменяет визуальную сверку с PDF.

## Исходное оглавление списком

Оглавление может занимать одну единицу Markdown со списком строк. Решение
`source_toc` сохраняет его место и порядок; каждая исходная строка должна точно
совпадать с `entries.source_text` и иметь проверенную цель `target`.
Сборщик убирает маркеры списка, отточия и старые номера страниц, затем ставит
гиперссылки. Номер внутри заголовка (например, «Сцена 1») сохраняется.
Несовпадение строки или неоднозначная цель останавливает сборку.

## Абзац, ошибочно включённый OCR в заголовок

Решение `display_roles` с `role: heading_prose_split` содержит `unit`
(`unit_id`, `ru_sha256`), точный `heading_text`, `source_evidence` и `reason`.
Для простого заголовка без вложенной разметки сборщик оставляет указанный
начальный текст заголовком, а продолжение переносит в обычный абзац.
Слова, исходная закладка и ссылки сохраняются; MASTER_RU не изменяется.
Неверный префикс, устаревший хеш, пустое продолжение и сложная вложенная
разметка останавливают сборку. Такое решение требует сверки с источником.

Если целый предварительный Markdown-заголовок на исходной странице является
обычным абзацем, `display_roles.role=prose_presentation` привязывает его
`unit_id` и `ru_sha256`, проверенное `source_evidence` и причину. Эта роль меняет
только HTML-тег целого заголовка на `p`; текст, вложенное выделение, ID и
входящие ссылки сохраняются. Ложный заголовок исключается из автоматически
созданного оглавления. Разбитый, неоднозначный или структурно вложенный блок,
устаревшая привязка и конфликтующее решение о том же блоке останавливают
сборку. Исходный `MASTER_RU.md` не меняется; окончательное визуальное решение
принимается после проверки DOCX.

## Предложение, разорванное иллюстрациями или врезкой

`interrupted_prose_reflow` задаёт две точные привязки в `units`, полный
упорядоченный список `intervening_units`, `source_evidence` и `reason`.
По умолчанию промежуточные единицы могут быть только изображениями, цитатными врезками
или маркерами исходных страниц. Продолжение присоединяется к первому абзацу
или пункту списка; изображения и врезки остаются после связного текста,
сохраняя взаимный порядок. Закладка продолжения сохраняет исходную страницу.
Неполное покрытие, устаревшие хеши, посторонний обычный текст и структурные
блоки на концах такой связки запрещены. Это правило не изменяет MASTER_RU
и не отменяет проверку конечного DOCX.

Если между частями находится печатный текстовый handout, решение может
добавить необязательный закрытый список `intervening_handout_groups`. Каждая
группа содержит непустые упорядоченные `units`, точную привязку `title`,
`source_evidence` и `reason`. Группа покрывает только непрерывную цепочку
заголовков, абзацев и таблиц; её `title` должен быть одним из её заголовков.
Все обычные промежуточные единицы должны быть покрыты группами ровно по
одному разу. Узлы handout, их порядок, текст, закладки и ссылки сохраняются;
неполные, перекрывающиеся, устаревшие или переупорядоченные группы останавливают
сборку. Без этой явной группы обычный текст по-прежнему запрещён.

Для уже существующего полного списка подписей карты можно добавить закрытый
`intervening_asset_labels`: точные привязки целого плоского списка и следующего
за ним исходного изображения на той же странице, плюс проверенное свидетельство
и причину. Список, повторы подписей и исходные байты изображения сохраняются.
В том же полном интервале допускаются только отдельно проверенные решения
`source_furniture_text` и удаления повторного заголовка; сами промежуточные
привязки не разрешают удаление. Порядок ролей не влияет на результат.
Для этого маршрута сборка и повторная проверка DOCX сверяют исходные страницы,
целый абзац с перенесённым продолжением, закладки, подписи и связь Word с
исходным изображением. Удалённый или изменённый текст, карта, граница страницы
или закладка продолжения блокируют проверку пакета.

## Точный перенос целого блока

`display_roles.role=reviewed_block_relocation` переносит целые блоки в представлении
для DOCX, сохраняя MASTER_RU. Решение содержит точные `units`,
`destination` (`position: before|after`, `unit`), полный `crossed_units`,
отпечатки `rendered_preimage`, `source_evidence` и `reason`.
Привязки единиц состоят из `unit_id` и `ru_sha256`. До изменения проверяются
исходный интервал, владелец блока, разметка и порядок всех пересекаемых блоков.
Для обычной подписи перед следующим блоком разрешён `keep_with_next: true`.
После сборки проверяются закладки, порядок абзацев, сохранность изображений
и связь подписи со следующим блоком в фактическом DOCX.

Если заголовок назначения повторяется на одной исходной странице, роль может
содержать `heading_occurrence: {ordinal, cohort}`. `ordinal` — индекс от нуля;
`cohort` — полный упорядоченный список точных привязок всех одинаковых
заголовков этой страницы. Свидетельство относится только к `destination.unit`.
Проверяются исходные байты, уровень и вложенное оформление заголовков,
полнота списка и соответствие тем же узлам HTML до переноса. Неполный список,
другой порядок, устаревшие хеши, изменение владельца или неоднозначное
назначение без свидетельства останавливают сборку. Выбор первого совпавшего
текста не применяется. Повторы остаются в документе.

## Целые группы характеристик

`reviewed_statblock_group` связывает проверенную последовательность целых
полей в одну карточку через `group_id`, точные `units`,
`rendered_members`, `source_evidence` и `reason`. При включённом
`statblocks.keep_together` сборщик ставит Word keepLines для всех членов
и keepNext для внутренних членов группы. Текст, значения, стили полей
и границы исходных страниц не переписываются. Проверка фактического DOCX
контролирует состав, порядок, закладки и флаги группы; автоматический
успех проверки не заменяет просмотр страниц после сборки.
