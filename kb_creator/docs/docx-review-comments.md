# Адресные замечания в DOCX

## Проверенное удаление дублей текста при сборке

В `reader_options.json` роль `omit_extraction_duplicate_text` удаляет только
целый текстовый абзац, для которого рецензент установил один исходный экземпляр
на той же странице PDF. Решение указывает точные идентификаторы и хеши удаляемой
и сохранённой RU единицы, порядковые номера совпадающих абзацев, интервал
символов сохранённого текста и локальную копию проверенного изображения страницы
под `evidence/`. Интервал охватывает все символы удаляемой единицы без исправления
регистра, пробелов, знаков или чисел. Разные решения могут ссылаться на один
сохранённый абзац. Решения для другого исходного повторения требуют отдельной
проверки; совпадение текста само по себе удаления не разрешает.

Сборка сохраняет исходный `MASTER_RU.md`. В `READER_PROJECTION.json` и манифесте
DOCX отражены отдельные `omitted_text_duplicates` и последовательность абзацев
затронутой исходной страницы. Проверка пакета заново применяет решения из
архивных входов и сверяет реальный поток абзацев `word/document.xml` между
закладками исходных страниц. Она также проверяет наличие сохранённого блока и
не принимает подмену отчётных счётчиков за доказательство удаления. Новая
языковая версия требует повторной проверки единиц, интервала и порядка
совпадений; изменение любого из двух текстов требует нового решения.

## Проверенные исходные артефакты в reader-версии

Роль `omit_source_artifact` принимает две дополнительные точные альтернативы с
`text_policy=reviewed_whole_plain_block_v2`: `source_furniture_text` для целого
абзаца печатного номера страницы/колонтитула и
`duplicate_text_represented_by_retained_artwork` для целого простого абзаца,
включая многострочную OCR-выжимку, уже видимую на сохранённом факсимиле.
Каждое решение привязывает конкретную RU единицу, исходную страницу, сырой текст,
локальный снимок PDF, область на снимке, проверившего человека и его вывод.
Второй вид дополнительно привязывает единицу изображения на той же странице и
точные байты исходного изображения. Нерецензированный текст и частичное удаление
строк этим маршрутом не поддерживаются.

Оба вида используют общий с текстовыми дублями свидетельский поток абзацев
исходной страницы. Повторная проверка DOCX сверяет этот поток, наличие
сохранённого изображения в нужном абзаце Word, его внутреннюю связь с исходными
байтами и отсутствие обрезки. Старые однострочные решения для изображения тоже
включаются в общий поток при новой сборке; формат старых решений сохраняется.
Перенос reader-решения в другую языковую версию возможен только при неизменных
удаляемом тексте, сохранённом изображении и доказательствах.

Пользователь вычитывает книгу в DOCX и возвращает отредактированный файл.
Нерешённый вопрос должен быть виден рядом с нужным текстом как обычный
комментарий Word. Однозначные ошибки исправляются до передачи книги.

## Текущий статус

Реализован отдельный модуль `pipeline/docx_review_comments.py` и служебная
команда `scripts/annotate_docx_review.py`. Интеграция с общим маршрутом
review-draft, автоматический перенос вопросов из реконструкции/перевода и
разбор возвращённого пользователем документа ещё не завершены. Наличие
комментариев не означает готовность пакета к передаче или принятие книги.

## Выбор чтения при переводе

Целевой порядок: скрипт передаёт точные альтернативы OCR в задание документального
перевода; переводчик выбирает чтение и сохраняет решение в данных. Из этих решений
скрипт создаёт отдельную версию английского мастера, затем задания перевода и
русский мастер. Отдельная пользовательская проверка исходных страниц не требуется.
Содержательные сомнения, оставшиеся после выбора чтения, доходят до адресных
комментариев в итоговом DOCX. Отсутствующий материал или невозможность привязать
фрагмент остаются ошибками пайплайна.

Это направление зафиксировано для дальнейшей интеграции. Координатор выбора,
полный перенос привязок EN → RU и автоматическое включение вопросов в DOCX ещё
не реализованы; отдельный аннотатор ниже уже работает.

## Вход и выход

Входы: исходный DOCX и реестр `kb_creator.docx_review_issues.v1` с точным
`docx_sha256`. Каждая запись содержит уникальный `issue_id`, `reader_anchor`,
`target_text`, `reason`, `source_page`, `en_excerpt` и необязательный `proposal`.
Якорь соответствует HTML id, перенесённому сборщиком в закладку Word.
Текст должен однозначно находиться в абзаце этой закладки, включая ячейку таблицы.

Выходы: новый DOCX с нативными комментариями и JSON-отчёт с привязками и хешами.
Исходник сохраняется. Повторное использование существующих выходных путей
запрещено. Устаревший хеш, отсутствующий якорь, неоднозначный текст или
неподдерживаемая структура абзаца должны завершать команду ошибкой.

Служебный вызов из корня репозитория:

```powershell
python -B kb_creator/scripts/annotate_docx_review.py `
  --source working/review/document.docx `
  --issues working/review/issues.json `
  --output working/review-next/document.docx `
  --report working/review-next/comment-bindings.json
```

Этот вызов предназначен для интеграции в сборку. Пользователь не должен
самостоятельно составлять реестр или находить технические якоря.

## Правила вопросов и проверки

- Комментарий описывает конкретную неоднозначность, выбранное чтение и источник.
  Технические TODO и незакрытые административные статусы не являются вопросами.
- Пропуски страниц, текста, таблиц, ассетов и неподтверждённые изменения чисел
  блокируют сборку. Комментарий не заменяет проверку полноты.
- Пустой список вопросов допустим для книги; сборка тогда пропускает аннотатор.
  Отдельный аннотатор предназначен для непустого списка.
- Перед передачей обязательны чтение всего собранного DOCX, просмотр всех его
  страниц и независимый release-review готовности именно к вычитке.
- PDF-превью может не показывать комментарии. Проверка страниц подтверждает
  вёрстку, а проверка OOXML — структуру и привязки комментариев; это разные проверки.
- Возвращённый файл сохраняется новой ревизией. Удалённый комментарий или
  неизменённый текст сами по себе не считаются принятием решения.
