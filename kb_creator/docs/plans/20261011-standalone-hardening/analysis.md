# KB Creator — анализ проделанной работы

- Дата: 2026-10-12. База: `f6cf348`.
- Метод: пять параллельных read-only аудитов (архитектура `pipeline/`; скрипты,
  контракты и снимки; тесты; протокол агентов и проверки; документация и
  процесс). Ключевые утверждения каждого перепроверены по коду. Тесты и
  конвейер не запускались, все цифры получены статически.
- Вопрос: насколько проект соответствует идее и что нужно, чтобы он стал
  самостоятельным конвейером с набором инструментов и подключаемыми агентами.

## 0. Вердикт

**Идея правильная, ядро ценное, оболочка непригодна для самостоятельной
работы.** Проект вырос как исследовательский процесс, оптимизированный под
доказуемость каждого шага в мульти-модельной команде, а не под поток книг.
Вокруг ~20 тыс. строк действительно полезного ядра накопилось:

- ~9 тыс. строк кода `pipeline/`, недостижимого из текущего маршрута;
- ~19 тыс. строк сценарных скриптов и ~54 тыс. строк снимков кода в `inputs/`;
- более 3 строк документации и доказательств на строку кода.

Механизмы самозащиты (хеш кода в идентичности прогона, неизменяемые
submission, повторная перевалидация всего) мешают как исправлять код, так и
вести книгу.

Сделать из проекта самостоятельный конвейер **реально**, но не постепенным
«допиливанием» текущей структуры. Нужен подход **«извлечь ядро, построить новую
тонкую оболочку»**: новый раннер со стадиями, адаптерами инструментов и
адаптерами агентов, который переиспользует проверенные модули, а историю
выносит в архив.

## 1. Соответствие идее

| Элемент идеи | Состояние | Оценка |
|---|---|---|
| Неизменяемые входы, SHA-256-идентичность | Последовательно реализовано (`pipeline/identity.py`, seal, inventories) | ✅ сильная сторона |
| Многовидовая OCR-реконструкция вместо доверия одному OCR | Три вида MinerU + сравнение + аудит покрытия (`scripts/audit_mineru_ai_merge_fidelity.py:303-424`) | ✅ лучшая часть системы |
| Отделение реконструкции, перевода и оформления | Есть: MASTER_EN → черновик → MASTER_RU → проекция → DOCX | ✅ |
| Сохранение чисел, кубов, якорей и структуры при переводе | Есть сигнатура строк (`scripts/scenario_master_ru.py:167-211`) | ✅ (местами слишком строго, см. §5) |
| Раздельные состояния приёмки | Есть, явно разведены | ✅ |
| Возобновляемость | Есть (`five_step.py`, нумерованные попытки, `status` только читает) | ✅ |
| **Самостоятельная работа без внешнего workspace** | Нет: `CoC/`, `MinerU/`, `.tools` — соседние каталоги NRI (плюс технический пункт D1, см. §13) | ❌ |
| **Подключаемые агенты** | Нет адаптера, схем заданий, разбиения на чанки, повторов | ❌ |
| **Подключаемые инструменты** | Шов есть (`StageAdapter`), но MinerU/PowerShell/Word зашиты | ⚠️ |
| **Новая книга без ручной сборки JSON** | Нет: три запечатанных артефакта без генераторов | ❌ |
| **Исправление ошибки без перезапуска книги** | Нет: любое изменение кода делает прогон stale | ❌ |
| Только DOCX как результат | Политика есть; маршрут исправлений (`successor`) для v3 не работает | ⚠️ |

## 2. Что сделано хорошо (сохранить)

1. **Примитивы идентичности.** `identity.py` (86 строк) и `manifests.py`
   (36) маленькие и чистые, отвергают symlink и выход за корень.
2. **Аудит покрытия реконструкции (Stage05).** Каждая непустая единица
   исходника должна быть выбрана, признана эквивалентной или исключена с
   причиной. Recall ≥0,95, ловятся повторные подстановки. Это настоящая
   защита от потери текста.
3. **Сигнатура структуры перевода.** Класс строки, числа, кубы, якоря,
   ссылки, картинки, ячейки таблиц. Плюс проверка целевых терминов глоссария
   (`five_step_language.py:248-276`).
4. **Конечный автомат `five_step`.** Явные фазы, попытки `name-NNN` без
   перезаписи, ошибка пишется в state, а не роняет процесс, `status` только
   читает, legacy-прогоны доступны только на чтение.
5. **Протокол «task → template → submission»** с привязкой `task_sha256`.
   По форме он не зависит от конкретного агента, это хорошая основа для
   адаптера.
6. **Внедряемые адаптеры** (`reconstruction.py:66-71`,
   `reconstruction_replay_resume.py:501`, `export=` в рендере). Шов для
   инструментов уже заложен.
7. **`process.run`**: без shell, с ограничением и санитизацией вывода и
   белым списком переменных окружения.
8. **Явное отключение старого маршрута** (`__main__.py:342-345`; DOCX-пакет
   отвергает HTML/PDF).
9. **Правила процесса, которые стоит сохранить:** seed-дефект → класс
   дефектов → общее исправление + тест; новый корень прогона вместо правки на
   месте; независимое ревью перед выпуском; журнал технического долга.

## 3. Что плохо: системные проблемы (по убыванию влияния)

### 3.1 Хеш исходного кода — часть идентичности прогона

`five_step._codes` хеширует ~60 файлов реализации для шага 1 и проверяет их
при каждом resume (`five_step.py:64-80, 149-151`). Любая правка, даже в
legacy-CLI (`__main__.py` входит в список), убивает текущие прогоны
(«verified successor required»). Вместе с неизменяемыми submission это дало:

- пилот Cursed Idol прошёл прогоны r01–r07;
- около 20 модулей successor/rebind/continuation/replay/recovery/revision
  (~8,8 тыс. строк) существуют в основном для обхода этого ограничения;
- реальные книги в итоге шли скриптовыми цепочками **в обход** state machine
  (`PROJECT_STATUS.md:5,87`).

Хеш бинарника инструмента тоже входит в идентичность, поэтому обновление
LibreOffice или Poppler тоже инвалидирует прогоны.

**Правильно:** версия пакета + хеш lock-файла + версии схем; политика
инвалидации по стадиям; операция «форк прогона с шага N с переопределениями».

### 3.2 Агенту приходится вручную собирать запечатанные JSON

До старта нужны `SOURCE_GRAPHICS_INVENTORY` (у него нет даже CLI, только
Python API) и `SOURCE_GRAPHICS_REVIEW`: постраничный обзор всей книги, который
пишется вручную. В середине прогона нужны `reader_options` и
`reader_fidelity_plan.v2`. **Генератора нет ни у одного из них.** Агент сам
считает `options_sha256`, `plan_sha256` и line-span sha256. План привязан к
хешам MASTER_RU и конфига, поэтому при любой их правке его пишут заново
(`five_step.py:387-391, 534`).

Реальные постраничные решения на практике порождались 2 267-строчным
`scripts/author_reviewed_semantic_decisions.py` по спецификации, а не по
заданию конвейера.

### 3.3 Монолитные submission, нет разбиения на части и dry-run-проверки

- Черновик перевода — одна submission на всю книгу (~880 единиц для
  52 страниц), хотя задание уже нарезано на пакеты ≤3000 символов
  (`five_step_language.py:281-294`).
- Обзор текста DOCX — тысячи блоков в одном файле.
- Проверки «только валидировать, не меняя состояние» нет: валидация живёт
  внутри `resume`. Ошибка в submission реконструкции сжигает прогон.

### 3.4 Агентов как подсистемы нет

«No automatic model backend» (`docs/five-step-usage.md:165`). Нет адаптера,
промптов (кроме 1–5 строк инструкции в задании), JSON-схем для заданий и
submission шагов 3–5, intake, reader options, текстового и визуального обзора,
повторов, бюджета, параллелизма. Роль ревьюера зашита строкой
`"codex_content_executor"` (`five_step_intake.py:389,448`).

### 3.5 Слой инструментов завязан на Windows и NRI

- MinerU запускается через PowerShell и `run_mineru_three_view.ps1`, который
  подключает `..\..\MinerU\scripts\profile-common.ps1`.
- В коде зашиты `.venv\Scripts\mineru.exe` и `python.exe`
  (`mineru_cpu_first.py:171-172`, `reconstruction.py:456`).
- Используются Windows Job Objects (`windows_process_tree.py`, 450 строк),
  `icacls` (`normalize_publication_access.py:39-45`, вызывается из
  `five_step_docx`).
- `powershell.exe` зашит, хотя в runtime есть ключ для него
  (`five_step_docx.py:903`).
- `subprocess.run` вызывается **без таймаута** (`process.py:76`).

### 3.6 Прогоны нельзя перенести

`state.json` хранит абсолютные пути к источнику, глоссарию, inventory, review,
плану и конфигу (`five_step.py:208-216, 231, 459, 485`), а evidence хранится
относительно корня прогона. Смешанная схема: при переносе каталога прогон
ломается.

### 3.7 Текущий маршрут частично сломан

- `five_step_successor.py:76` принимает только прогоны v1/v2, а новые — v3.
  **Маршрут исправлений после ревью для новых книг не работает**, и к тому же
  пропускает текстовый обзор (`:251-252`).
- `pipeline/__init__.py` и `__main__.py:31-53` при любом импорте загружают
  закрытый publication-маршрут (~3,4 тыс. строк) и его скрипты.
- `doctor` — заглушка, которая возвращает константу.

### 3.8 Логика конкретных книг внутри «общего» кода

- `pipeline/reviewed_docx_revision.py:382-431` содержит id решений Kremlin и
  Leningrad (`kremlin-chr-app-crosswalk`, `len-stealth-context-values`, …).
- `scripts/merge_translation_batches.py:143` (код шагов 3/4) пишет заголовок
  `# The Innsmouth Terror - Source Text Full RU`.
- `build_scenario_master_en.py` и `verify_scenario_master_en.py` содержат
  ~50 привязок к Viral (`scenario_id != 'viral'`, 168 якорей, список хешей
  ассетов). При этом они числятся в `DEPENDENCIES` шагов 2/4 только ради
  хеша кода и в маршруте **не выполняются**. Правка неиспользуемого
  Viral-кода инвалидирует прогоны.
- `"hit_points"`, CoC-регулярки навыков, `--system choices=["coc"]`, автор
  DOCX «NRI» — доменная логика без отдельного «доменного пакета».

### 3.9 Конвейер зависит от скриптов

28 модулей `pipeline/` содержат 74 импорта из `kb_creator.scripts`, из них 24
импортируют приватные `_функции` (например,
`five_step_language.py:7`: `legacy._source_units`). Граница
«библиотека / CLI-утилиты» перевёрнута.

### 3.10 Сложность

- `reader_projection.py:134` `project_reader_html` — **одна функция на
  ~1 740 строк**, около 200 `raise` и 14 вложенных функций.
- Ещё пять функций по 250–335 строк, вложенность до 9 уровней.
- `raise` встречается в среднем раз на 9 строк.

## 5. Лишние и формальные проверки

**Содержательные — оставить как ядро приёмки:**

- покрытие реконструкции (Stage05);
- сигнатура чисел и структуры при переводе;
- целевые термины глоссария;
- проекция статблоков и выравнивание RU-спанов;
- закрытие размещения графики;
- идентичность входов.

**Формальные (самоаттестация), стоимость выше пользы:**

- текстовый обзор DOCX: агент проставляет `read:true` на каждый из тысяч
  блоков, а findings могут быть только `resolved` (`docx_text_review.py:208,
  219, 230`). Сообщить о дефекте в этом канале **невозможно**;
- визуальный обзор: проходит только `reviewed:true, findings:[]` на каждой
  странице (`five_step.py:512`), а `reviewer_role: "agent"` закрывает
  финальный gate. Реальная проверка в пилоте шла вне конвейера;
- `_agent_authority` пишет сам Python с захардкоженной ролью и текущим
  временем (`five_step_intake.py:379-390`);
- `SOURCE_DISPOSITION` проставляет каждой странице `"reader"` /
  `"closed_reconstruction_review"` (`five_step_intake.py:533-537`);
- счётчики `section_reviews` в fidelity-плане ни с чем не сверяются
  (`reader_fidelity.py:110-126`).

**Избыточная перевалидация, дорого:**

- `_load` при **каждом** `status`/`resume` перехеширует все evidence,
  включая деревья MinerU (`five_step.py:141-148`);
- `validate_produced_inventory` **заново рендерит каждую страницу PDF**
  (`source_graphics.py:110-138`), а вызывается он транзитивно через
  `validate_review` → `validate_plan`. Последний вызывается из
  `five_step.py:380, 478`, `five_step_docx.py:723` и ещё ~7 мест в
  `reader_fidelity.py`. По графу вызовов это порядка десятка полных
  перерендеров книги на одну сборку DOCX;
- `verify_language_result` пересчитывает работу черновика и вычитки перед
  каждой сборкой DOCX.

**Слишком строгие:** равенство эмфаза построчно при переводе блокирует
естественные русские перестановки.

**Как правильно:**

- валидировать один раз на кортеж идентичностей и кешировать результат;
- обзоры заменить отчётами с findings, которые запускают адресную
  пересборку;
- ревьюера определять метаданными исполнителя, а не литералом.

## 6. Тесты

- 224 тестовых модуля, ~54 тыс. строк, ~2 300 `def test_` и ~420
  parametrize. Нет `conftest.py`, `pytest.ini` и маркеров для медленных и
  внешних тестов.
- **72 из 224 (32%) упадут на импорте в чистом окружении:**
  - 33 — из-за импорта `translator` (закрывается техническим пунктом D1,
    см. §13);
  - 21 — из-за `reportlab`;
  - 15 импортируют несуществующие `pdf_raw.page_proof/raw_authority_*/errors/source_reconstruction`;
  - 1 — из-за `mineru`.
- Ещё десятки тестов упадут при выполнении: отсутствуют `MinerU/`, `.tools`,
  `working/`, `CoC/`; есть путь `D:\NRI`.
- ~8,4 тыс. строк тестов поддерживают закрытый publication-маршрут, ~3 тыс. —
  разовые скрипты Innsmouth/Viral, ~8,3 тыс. — мёртвый `pdf_raw`. Есть тесты,
  которые grep'ают исходный код, и тест с побайтовым сравнением снимка
  `translator.py`.
- 55 тестовых файлов импортируют друг друга. Тесты текущего маршрута тянут
  `test_publication_control_plane`.
- **Пробел:** нет сквозного теста настоящих модулей от синтетического PDF до
  DOCX с фейковым агентом (`test_five_step_runner` подменяет все шаги на
  `SimpleNamespace`). Никто не запускает `python -m kb_creator translate
  run/resume` целиком. Отказ внешних инструментов не тестируется.
- Сильная сторона: путей отказа (tamper, stale, reseal, resume) покрыто
  много, и это реальная ценность.

## 7. Документация и процесс

- Checkout около 640 МБ. **Код и тесты — ~1,4% байт** (~9 МБ).
- Прозы около 195 тыс. строк против 88,8 тыс. строк кода (2,2:1). С
  JSON-доказательствами соотношение 3,7:1.
- В `docs/plans` 39 goal-пакетов и **1 056 handoff/receipt** (8,2 МБ).
  Верификация и переделки занимают ~55% их объёма. Встречается 196
  «remediation», 26 «retry», до v06 раундов. Один пакет
  (`20260830-kb-creator-next-scenario`) — 570 файлов.
- `PROJECT_STATUS.md`: 5 148 строк, 190 неопределённых N-кодов, ~278
  «склеенных» токенов («all367pages», «exact43filefreeze»). Записи от 11
  октября нет, новому человеку файл не читаем.
- `README.md`: актуальны только строки 1–21 (~3%); ~90% описывают закрытый
  маршрут, причём с рабочими на вид командами. 49 из 180 относительных
  ссылок битые. Лучшие обзорные документы (`docs/handoff/*`) из README не
  ссылаются.
- `reports/`: 116 PNG-скриншотов QA на 50 МБ вне LFS, вопреки собственному
  правилу «не коммитить скриншоты».
- `inputs/` (~330 МБ) — почти целиком история закрытого маршрута. Тесты
  ссылаются на него в трёх местах. Для четырёх книг из `deliverables/`
  (Cursed Idol, Kremlin, Leningrad, Fear) мастеров в репозитории нет.

**Что стоит сохранить из процесса:**

- лёгкий goal-пакет `plan/context/release`;
- независимое ревью перед выпуском;
- четыре состояния приёмки;
- журнал долга.

**Что избыточно:**

- receipts на каждый под-шаг с несколькими раундами critic/rereview в Git;
- ролевая матрица моделей;
- append-only статус с N-кодами;
- снимки кода в каждом пакете;
- скриншоты QA в Git;
- несколько датированных «accepted»-копий одного мастера.

## 8. Готовность к самостоятельному конвейеру: блокеры

1. Хеш кода и инструментов в идентичности + неизменяемые submission (§3.1).
2. Нет генераторов обязательных запечатанных артефактов (§3.2).
3. Монолитные submission без разбиения на части и dry-run (§3.3).
4. Нет агентной подсистемы (§3.4).
5. Слой инструментов завязан на Windows и NRI-раскладку (§3.5).
6. Внешние зависимости: CoC, MinerU, `.tools` (D2, D4).
7. Сломанный successor для v3 (§3.7).
8. Тестовый набор не собирается в чистом окружении (§6).

Ни один из этих блокеров не означает, что идею надо менять. Это всё свойства
оболочки, а не ядра.

## 9. Что переделать в принципе: целевая архитектура

```
kb_creator/
  core/        identity, seal, atomic IO, jsonschema-валидация (одна реализация)
  runner/      реестр стадий, state (относительные пути), кеш валидации,
               fork-from-step, dry-run validate
  stages/      reconstruct, master_en, draft, proofread, reader, docx, review —
               каждая объявляет inputs/outputs, task-schema, submission-schema,
               run() и accept()
  tools/       ToolSpec: probe/version/invoke; провайдеры: mineru, pdftoppm,
               libreoffice, (word — опционально, Windows)
  agents/      AgentExecutor: task → submission; реализации: file-drop (человек),
               Claude, другие; чанкинг, повторы при ошибках валидатора, бюджет,
               параллельность; seal делает Python, не LLM
  domains/coc/ глоссарий (пин D2), навыки, статблоки, hit_points, раздатки
  legacy/      (или архивная ветка) publication, сценарные скрипты
```

Ключевые принципы:

1. **Идентичность прогона** = входы + версия пакета/lock + версии схем
   стадий. Обновление кода не убивает прогон, если схема стадии не
   изменилась.
2. **Генераторы вместо ручного JSON:**
   - inventory — CLI;
   - source review — заполняется заранее из inventory и image-блоков MinerU,
     агент только подтверждает или исправляет постранично;
   - fidelity plan выводится из review и проекции;
   - reader options имеют разумные умолчания.
3. **Обзоры с findings.** Текстовый и визуальный обзор возвращают дефекты,
   а дефект запускает адресную пересборку. Ревьюер — метаданные исполнителя.
4. **JSON-схемы — единственный источник правды**, одна цепочка миграций на
   семейство вместо параллельных читателей.
5. **Переносимые прогоны.** Пути относительно корня прогона или
   content-addressed копии; машинно-локальное — в незапечатанном
   `local.json`.
6. **Валидация один раз на идентичность**, с кешем.
7. **Декомпозиция `project_reader_html`** на последовательность проходов.

## 10. Что убрать из основного дерева

Убирать в архивную ветку или тег; в `ARCHIVE.md` записать хеш.

| Что | Объём |
|---|---|
| publication-маршрут (`publication.py`, `publication_adapters.py`, 9 скриптов (e), их импорты из `__init__`/`__main__`) | ~7,6 тыс. строк + ~8,4 тыс. строк тестов |

## 11. Влияние на решения D1–D9

Все решения D1–D9 остаются верными, но меняется порядок работ:

- **Сначала сокращение и архивирование (§10).** Без него hardening придётся
  делать и для кода, который будет удалён.
- **Затем новая оболочка (§9)** поверх оставшегося ядра. D2 (пин словаря),
  D4 (инструменты) и D6 (pyproject) реализуются уже внутри неё, а не латками
  к `five_step.py`.
- **D3 (три DOCX) и чистку документации можно делать сразу**, они ни от чего
  не зависят.

## 13. Технический пункт: импорт `translator` (D1)

Это не архитектурная проблема. Актуальный код весь в `kb_creator`, но
`five_step_docx.py:28` и модули `reader_*` содержат
`from translator.translator import ...`, а в NRI пакет `translator` лежал
рядом с `kb_creator`. В отдельном репозитории его нет, и импорт не проходит.

Замер по NRI `translator/translator.py` (14 085 строк): маршруту нужны 14
функций и констант, ~420 строк (`markdown_to_review_html`, `slugify`,
`unique_slug` и то, что они вызывают). Они переносятся в `kb_creator`
по D1, после чего 33 тестовых модуля и DOCX-шаг перестают зависеть от NRI.
