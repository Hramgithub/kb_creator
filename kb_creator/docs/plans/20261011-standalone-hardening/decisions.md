## D1. Пакет `translator`

Дата: 2026-10-11.

### Ответ владельца

Пакет находится в репозитории `https://github.com/Hramgithub/NRI`, локально — в
рабочей копии NRI на этой машине. Зависимость KB Creator от него владелец
считает нежелательной.

### Проверенные факты (read-only)

- В локальной рабочей копии NRI (ветка `main`) каталог `translator/` есть.
  Последний коммит, затрагивающий его: `3c7823af` от 2026-09-21. Незакоммиченных
  изменений в каталоге нет.
- KB Creator использует только модуль `translator/translator.py`
  (≈665 KB, один файл).
- Текущий маршрут (`kb_creator/pipeline/`: `five_step_docx.py`,
  `reader_projection.py`, `reader_duplicate_text.py`, `reader_options_rebind.py`,
  `reader_statblock_grouping.py`) импортирует только три функции:
  `markdown_to_review_html`, `unique_slug`, `slugify`.
- Широкий API `translator` (около 45 функций: `build_production_html`,
  `build_production_pdf`, `run_release_qa` и др.) используется только
  историческими HTML/PDF-скриптами Innsmouth/Viral
  (`scripts/build_innsmouth_*`, `scripts/build_viral_production.py`,
  `inputs/viral/production/pipeline/*`) — это закрытый publication-маршрут.
- `pipeline/five_step.py:79` учитывает `ROOT/translator/*.py` в inventory
  реализации шага 5 через glob. Если каталога нет, glob молча возвращает пустой
  список: зависимость пропадает из inventory, а не вызывает ошибку.

### Решение

**D1b — принято (2026-10-11): извлечь функции.** Владелец выбрал
рекомендованный вариант.

- `markdown_to_review_html`, `unique_slug`, `slugify` и их транзитивные
  внутренние помощники переносятся в отдельный модуль внутри
  `kb_creator/pipeline/`. Замер AST-обходом (2026-10-12): 14 символов,
  ~420 строк из 14 085 строк `translator.py`. Импорты `translator` из текущего маршрута убираются.
- Эталон поведения — `translator/translator.py` из NRI на коммите `3c7823af`.
  В provenance модуля записываются его SHA-256 и коммит.
- Регрессионный тест: на фиксированном наборе входов (включая реальные
  MASTER_RU-фрагменты из `inputs/`) результат извлечённых функций байт-в-байт
  совпадает с эталоном. Эталонные выходы фиксируются один раз и хранятся в
  тестах, чтобы тест не зависел от наличия NRI.
- Inventory шага 5 (`five_step.py:79`) переводится на новый модуль. Молчаливый
  glob по отсутствующему каталогу убирается: отсутствующая зависимость должна
  вызывать ошибку.
- Исторические HTML/PDF-скрипты Innsmouth/Viral, использующие широкий API
  `translator`, не переносятся. Они остаются неисполняемым архивом закрытого
  маршрута; это нужно явно указать в документации.
- Существующие запечатанные прогоны с другим inventory шага 5 не
  пересчитываются: смена реализации делает их stale, что ожидаемо.

## D2. Общий словарь CoC

Дата: 2026-10-11.

### Ответ владельца

Словарь вынесен в отдельный репозиторий `https://github.com/Hramgithub/CoC`,
каталог `terminology/`. Канонический источник — этот репозиторий, а не NRI.

### Проверенные факты (read-only)

- `git ls-remote` показывает, что репозиторий доступен: `main` на
  `3b3979d67670f6dbdf5e7b1f1b7d058cb6be240f`.
- Локального клона этого репозитория рядом с проектами нет. Содержимое
  `terminology/` (имя и формат CSV) ещё не сверено.
- Старая копия в NRI (`CoC/Project_Reference/Terminology/CoC_Terminology_Decisions.csv`)
  имеет SHA-256 `8F6A41A6…E6800` — это тот же хеш, что был зафиксирован
  5 октября.
- `kb_creator/pipeline/coc_glossary.py:15` по умолчанию указывает на
  `ROOT/CoC/Project_Reference/Terminology/CoC_Terminology_Decisions.csv`, то есть
  на раскладку NRI. Этот путь в standalone-репозитории не существует.

### Решение

**D2b — принято (2026-10-11): пин через конфиг.**

- В репозитории хранится только небольшой отслеживаемый файл-пин (например,
  `kb_creator/reference/coc-terminology.pin.json`): URL
  `https://github.com/Hramgithub/CoC`, коммит, относительный путь CSV внутри
  `terminology/`, размер и SHA-256. Копия CSV в KB Creator не хранится.
- Локальный путь к клону CoC задаётся на конкретной машине: в
  `runtime.local.json` (не отслеживается) или явным `--shared-registry`.
- Неявный default `ROOT/CoC/Project_Reference/...` в `coc_glossary.py`
  удаляется. Для `--system coc` без доступного словаря запуск
  останавливается до создания run root.
- Если байты локального CSV не совпадают с пином, запуск останавливается до
  OCR. Обновление словаря делается явным сдвигом пина отдельным изменением.
- Уже запечатанные прогоны продолжают проверяться по своей сохранённой копии в
  `terminology/` внутри run (прежнее поведение); сдвиг пина их не трогает.
- Перед реализацией: клонировать CoC и сверить формат CSV в `terminology/` с
  тем, что ожидает `coc_glossary.py` (колонки, статусы `accepted` /
  `review_required`), и сравнить с NRI-копией `8F6A41A6…`.

## D3. Три исправленных DOCX от 5 октября

Дата: 2026-10-11.

### Ответ владельца

Обновлённые версии должны быть в Git-репозитории NRI.

### Проверенные факты (read-only)

- В NRI они закоммичены коммитом `9f9d47a0` (2026-10-05, «Fix reviewed DOCX
  and enforce DOCX-only source fidelity») по путям
  `kb_creator/working/user-review-20261004/{fear,leningrad,kremlin}-reader-v01/document.docx`.
  При выделении KB Creator весь `kb_creator/working/**` был исключён, поэтому
  они не попали в standalone-репозиторий.
- Эти же файлы есть в рабочей копии NRI, и их SHA-256 точно совпадают с
  release-записью цели `20261004-user-docx-review`:
  - Fear `D79AB0EC131D2C6926D868EB037786093F615AEAF122895AA4487254616CF33E`;
  - Leningrad `CC3A1F96D82121C07938D860EF88186AA33A32199B578D4C7C2DE05F4C83AD23`;
  - Kremlin `5573888152F7EDAB32D483E4D652FD465694BFBF1764CC708C3EF7C042AA87D8`.
- Тот же коммит NRI обновил проверенные пользователем оригиналы Fear и
  Leningrad в `deliverables/latest/`; эти версии (с ответами пользователя) в
  standalone уже есть, LFS-объекты `e8505b99…` и `3e2172ab…`.

### Решение

**D3b — принято (2026-10-11): рядом с оригиналом.**

- Целевые пути (Git LFS):
  - `kb_creator/deliverables/latest/fears-sharp-little-needles/corrected-v01/document.docx`;
  - `kb_creator/deliverables/latest/shadows-of-leningrad-1938/corrected-v01/document.docx`;
  - `kb_creator/deliverables/latest/secrets-of-the-kremlin-1931/corrected-v01/document.docx`.
- Источник — объекты из NRI-коммита `9f9d47a0`, байты переносятся без
  изменений. Перед копированием и после него сверяется SHA-256 с D3; при
  несовпадении перенос останавливается.
- Проверенные оригиналы `deliverables/latest/<книга>/document.docx` и их
  ассеты не меняются и не переименовываются.
- `deliverables/latest/README_RU.md` (строки 18–20) переводится на новые
  пути. `MANIFEST.json` дополняется тремя записями без переписывания
  существующих. Provenance (коммит NRI, исходный путь, хеш) записывается рядом.
- Статус файлов: технически одобрены в объявленной области (release
  `20261004-user-docx-review`); **не приняты пользователем**. Это указывается в
  README_RU.
- Нужно проверить `.gitignore`/`.gitattributes`: allowlist должен разрешать
  ровно эти три пути через LFS и не открывать `working/`.

## D4. Рендерер DOCX для визуальной проверки

Дата: 2026-10-11.

### Решение владельца

**Принято: LibreOffice из `.tools`** (+ Poppler `pdftoppm` для PNG).
Word COM не является поддерживаемым рендерером этого маршрута.

### Проверенные факты (read-only)

- В рабочей копии NRI есть `.tools/`, он игнорируется Git NRI. Там есть
  `LibreOffice/26.8.0`, `poppler/poppler-26.02.0`, `MinerU`, `python`,
  `tesseract`, `pytest`, `python-test-deps` и др.
- `.tools/tool-manifest.json` (схема `nri_local_pdf_tools_manifest.v1`,
  2026-07-08) устарел: в нём есть только Poppler 26.02.0 и Tesseract 5.4.0.
  LibreOffice, MinerU и Python не перечислены. Также в нём записаны
  абсолютные пути и имя машины.
- Код KB Creator жёстко требует инструменты под `REPO_ROOT/.tools`
  (`scripts/publication_render_qa.py:21-44`,
  `scripts/export_docx_to_pdf_local.py:21,108`) и отвергает reparse points
  (`export_docx_to_pdf_local.py:119`). Поэтому junction/symlink на NRI `.tools`
  не пройдёт проверку.

### Открытый вопрос

**D4b — принято (2026-10-11): runtime + пин сейчас, установка скриптом из
репозитория tools как целевое состояние.**

Этап 1 (в рамках standalone hardening):

- Жёсткая привязка к `REPO_ROOT/.tools` убирается. Корень инструментов
  задаётся в неотслеживаемом `runtime.local.json` (на этой машине это может быть
  существующий NRI `.tools`, без копирования).
- В KB Creator хранится отслеживаемый манифест ожидаемых инструментов:
  имя, версия, относительный путь исполняемого файла внутри корня, SHA-256.
  Абсолютных путей и имени машины в нём нет. Начальный состав: LibreOffice
  26.8.0 и Poppler 26.02.0 (`pdftoppm`); MinerU, Python и Tesseract — когда
  дойдёт очередь до шага реконструкции.
- Перед рендером проверяется, что фактические бинарники совпадают с
  манифестом. При несовпадении работа останавливается до создания вывода.
  Проверки reparse points и выхода за разрешённый корень сохраняются.
- Идентичность инструментов записывается в evidence прогона.

Этап 2 (целевое состояние, отдельная цель):

- Репозиторий `https://github.com/Hramgithub/tools.git` становится
  единственным источником проверенных инструментов: зафиксированные версии,
  хеши дистрибутивов, скрипты установки и обновления.
- KB Creator получает bootstrap-скрипт, который ставит инструменты из этого
  источника по манифесту, а пин указывает на конкретный коммит/версию
  tools-репозитория.
- Факт (read-only, 2026-10-11): `git ls-remote` возвращает пустой список refs,
  то есть репозиторий существует, но пока пуст. Конкретная ветка, о которой
  говорил владелец, ещё не создана или не видна. Структуру tools-репозитория
  нужно проектировать отдельно; бинарники крупные — решить LFS/Releases.

## D5. Правила работы (governance)

Дата: 2026-10-11.

### Решение владельца

**Принято: сжатый локальный `CLAUDE.md`** в корне репозитория (и `AGENTS.md`
с тем же содержанием или ссылкой, для других агентов).

- Источники: NRI `docs/governance/nri_goal_governance.md`, NRI `AGENTS.md`,
  правила из `kb_creator/README.md` (раздел Rules) и `MODEL_HANDOFF_SPEC.md`
  §5–6, §14. Перед написанием NRI-документы читаются read-only; в
  `CLAUDE.md` указывается provenance (коммит NRI).
- Содержание: неизменяемые входы (`Source/`, PDF, оригинальные DOCX, frozen
  packages, receipts); четыре раздельных состояния приёмки; fresh run root
  вместо правки на месте; что не коммитить (`working/`, рендеры, OCR overlays,
  профили, кэши, секреты, абсолютные пути); порядок чтения документов;
  goal-пакеты `plan/context/release` для многоэтапной работы; generic-исправления
  с тестами вместо разовых правок книги; commit/push только по явной команде
  владельца; поиск по репозиторию через `git grep` из-за default-deny
  `.gitignore`.
- Не переносится: ролевая матрица GPT-6 (sol/astra/luna) и привязка к
  конкретным моделям. Принцип независимого review (critic не участвует в
  реализации) сохраняется.
- Правила layout DOCX переносятся только если они действительно используются
  текущим маршрутом `five_step_docx_v3`. Иначе остаются ссылкой на историю.
  Решается при чтении NRI-документов.

## D6. Python-окружение и зависимости

Дата: 2026-10-11.

### Проверенные факты (read-only)

- Сторонние импорты в `kb_creator/{pipeline,scripts,tests}`: `docx`
  (python-docx), `fitz` (PyMuPDF), `jsonschema`, `lxml`, `pdfplumber`, `PIL`
  (Pillow), `pypdf`, `pypdfium2`, `reportlab`, `pytest`, `mineru`; плюс
  `translator` (см. D1).
- Python в NRI: `.tools/python/cpython-3.12.14` и `.tools/MinerU/.venv` —
  оба 3.12.14. Базовый интерпретатор venv MinerU — runtime Codex в профиле
  пользователя (`~/.cache/codex-runtimes/...`), то есть окружение привязано к
  чужому инструменту.
- В venv MinerU найдены: python-docx 1.2.0, lxml 6.1.1, Pillow 12.2.0,
  pypdf 6.16.0, pypdfium2 5.10.1, reportlab 5.0.0. Метаданных PyMuPDF,
  pdfplumber, jsonschema, pytest и mineru в нём нет: они разнесены по другим
  каталогам `.tools` (`pytest`, `python-test-deps`) или установлены иначе.
- Исторические тесты 5 октября шли на bundled Python Codex с pytest 9.0.2 из
  `D:/NRI/.tools/python-3.13.14/...`, то есть на другой версии и другой машине.
- Единого описания зависимостей нет ни в KB Creator, ни в NRI
  (`translator/requirements-dev.txt` содержит только `pytest==9.0.2`).

### Решение

**Принято (2026-10-11): `pyproject.toml` + `uv.lock`, Python 3.12.x.**

- `pyproject.toml` в корне: основные зависимости (python-docx, lxml, Pillow,
  pypdf, pypdfium2, PyMuPDF, pdfplumber, jsonschema, reportlab — точный список
  уточняется по фактическим импортам текущего маршрута) и группа `test`
  (pytest). `uv.lock` фиксирует точные версии и хеши.
- Стартовые версии берутся из проверенного окружения NRI (например,
  python-docx 1.2.0, lxml 6.1.1, Pillow 12.2.0, pypdf 6.16.0), а не
  «последние». Расхождения подтверждаются тестами.
- Venv создаётся локально и не отслеживается. Зависимости от интерпретатора
  Codex runtime быть не должно; uv берётся из `.tools` (D4), позже — из
  репозитория tools.
- Замечание для реализации: MinerU уже вызывается как отдельный процесс со
  своим Python (`runtime.reconstruction.python`, PowerShell-runner), поэтому
  его тяжёлое окружение (torch и пр.) логичнее описывать как инструмент в
  манифесте D4, а не включать в `uv.lock` пакета.

**Принято (2026-10-11): исходники в Git не хранятся, только реестр хешей.**

- Английские исходные PDF остаются у владельца (Яндекс.Диск). В Git они не
  добавляются ни обычным blob, ни через LFS.
- В репозитории ведётся отслеживаемый реестр источников (например,
  `kb_creator/reference/source-registry.json`): идентификатор книги, исходное
  имя файла, размер, SHA-256, издание/редакция, примечание о происхождении.
  Абсолютных путей и имени машины в нём нет. Начальные записи: Fear
  (`49CDBAD9…`, 69 575 583 байт) и Leningrad (`E8C21B6D…`, 2 800 661 байт);
  остальные добавляются по мере сверки.
- Локальный путь к PDF задаётся на машине (аргумент `--source` или
  `runtime.local.json`). Конвейер сверяет байты с реестром и останавливается
  при несовпадении.
- `.gitignore` остаётся fail-closed для `*.pdf`. Унаследованные от NRI
  правила для чужих проектов (`Dune/`, `CoC/` и т. п.) нужно вычистить
  отдельной правкой, не ослабляя запрет на PDF.

## D10. Новый проект Sourcefold (2026-10-12)

**Принято:** развитие переносится в новый чистый репозиторий
`Hramgithub/sourcefold`. Имя «KB Creator» не отражает суть. Sourcefold по

## D12. Цель и рамки Sourcefold — в обсуждении (2026-10-12)

Формулировка владельца:

- Цель Sourcefold: из PDF получить **документально точный структурированный
  материал, переведённый на русский**, плюс **набор артов** и **набор
  метаинформации**. Материал — это текст, таблицы, раздатки, статблоки
  персонажей. Подключается глобальный словарь терминов и определений.
- **DOCX и человеко-читаемый материал — отдельный проект**, не Sourcefold.
- Конечная цель — **единая база**, к которой можно обращаться за информацией
  по сценарию, правилам, таблицам, персонажам; её можно развернуть как
  веб-приложение для других пользователей и как модуль Foundry.

Следствие: выход Sourcefold — структурированный пакет данных, а не DOCX. Слой
reader/DOCX из kb_creator (~6+ тыс. строк, вместе с формальными обзорами и
перерендерами) в Sourcefold не переносится. Детали рамок обсуждаются по
вопросам, решения записываются как D12a, D12b и т. д.

### D12a. Глубина типизации статблоков в v1 (2026-10-13)

**Принято: полностью.** Модель данных — `schema-draft.md`. Характеристики,
производные значения, потеря рассудка, навыки, атаки (%, половина/пятая,
кубы урона, флаг БкУ, дальность, осечка, боезапас) и заклинания хранятся в
типизированных полях, рядом всегда `raw`. Извлечение и валидатор сущностей
обязаны покрывать все эти поля с первой версии.

### D12b. Конвертация старых редакций — отдельный конвейер (2026-10-13)

**Принято:** конвертация 5e/6e → 7e не входит ни в Sourcefold, ни в сборку
базы. Это **отдельный конвейер** обработки старых редакций.

- Sourcefold хранит только исходные значения (`raw` + `value`) и объявленную
  редакцию источника (`game.source_edition`, `character.edition`). Слоя
  `normalized_7e` в пакете Sourcefold нет; раздел `normalization/` из
  `schema-draft.md` §4 переносится в будущий конвейер конвертации.
- Спецификация конвертации U7 (`20261004-user-docx-review/audit/conversion/`)
  — исходный материал для этого будущего конвейера.
- Для пилота и первичной проверки модели берутся книги 7-й редакции, которые
  уже есть в репозитории. Владелец может позже дать «правильные» сценарии для
  анализа.

## D13. Объединение с git_coc (2026-10-13)

Предложение, принятое за основу обсуждения: Sourcefold и веб-помощник
`git_coc` объединяются **через общую модель данных**, а не через код.

- Общие JSON-схемы сущностей (персонаж, существо, заклинание, оружие,
  таблица, раздатка, термин, арт, источник). TS-типы для веба генерируются из
  тех же схем.
- Текущие данные git_coc (правила из русской книги) один раз переводятся в
  общий формат и становятся «пакетом правил». Sourcefold выдаёт пакеты
  сценариев в том же формате.
- Сборка базы объединяет пакеты и строит связи (NPC ↔ заклинание ↔ термин).
  Потребители: веб (UI и логика git_coc + раздел «Сценарии»), экспорт в
  Foundry (`nri-coc-library`), DOCX (отдельный проект).

**Структура репозиториев (монорепо или отдельные) — отложена.** Сначала
черновик схем сущностей, затем решение о репозиториях.
