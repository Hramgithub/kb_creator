# PDF_EN → русский DOCX: предложение целевого потока

Дата: 2026-09-19. Статус: **рабочее предложение пользователя для обсуждения**.
Связанный анализ: `docs/plans/20260919-kb-creator-translator-flow-analysis/`.
Этот текст не меняет принятые контракты существующих запусков KB Creator и
не назначает новый продуктовый namespace.

## Желаемый результат

Пользователь передаёт неизменяемый английский PDF и получает русский **DOCX
вместе с папкой используемых ассетов**. Он проверяет DOCX и может внести
постпродакшн-правки. После этих правок отдельный завершающий шаг создаёт
`PDF_RU` именно из проверенного DOCX. HTML не обязателен как пользовательский
выход. Полный ArtView не обязателен для обычного прохода и вызывается по
запросу или по отдельно согласованному правилу разрешения визуальной
неопределённости.

Внутренние артефакты нужны для контроля качества и повторяемости, даже если
пользователь получает только DOCX и ассеты:

```text
PDF_EN
  → MinerU: reconstruction.md + структурированные метаданные
  → очистка, порядок чтения, арт-якоря, смысловая структура: MASTER_EN
  → документальный перевод и литературная вычитка: MASTER_RU
  → иллюстрации, оформление таблиц и статблоков, макет: DOCX_RU + assets
  → проверка и правки пользователя в DOCX
  → по запросу: PDF_RU из точного проверенного DOCX
```

Сильные стороны, которые пользователь хочет сохранить: MinerU вместе с
метаданными, документальный перевод, литературная вычитка и пригодный для
дальнейшего редактирования DOCX.

Ключевая граница: `MASTER_RU` — **текстовая и смысловая authority**, а DOCX —
**основная точка издательской полировки**. В `MASTER_RU` остаются перевод,
заголовки, порядок, базовые ссылки/якоря и типы смысловых блоков, нужные для
безошибочной сборки. Выбор конкретной картинки, её размер, шрифт, отступы,
вид таблиц и статблоков, размещение по страницам и другие решения макета
относятся к DOCX-проекции. Это позволяет упростить повторяемый путь
`PDF_EN → reconstruction → MASTER_EN → MASTER_RU` без потери структуры источника.

## Отличие от действующего KB Creator

Действующий нейтральный публикационный контракт фиксирует
`accepted MASTER_RU + accepted ArtView/configs → HTML → accepted HTML → DOCX
→ accepted DOCX → PDF → package` (`kb_creator/README.md`). Реализация
`kb_creator/pipeline/publication.py` требует ArtView/HTML authority и выдаёт
одну стадию за один вызов. `kb_creator/scripts/production_docx.py` строит
DOCX из HTML. Это текущая реализация, поэтому HTML может пока оставаться
**внутренним промежуточным представлением** без обязанности выдавать и отдельно
принимать его как итоговый файл. Прямая сборка DOCX из структурированного
MASTER_RU — отдельный технический вариант, который надо сравнить по качеству
с существующим HTML→DOCX builder до выбора.

Ранний `translator` уже имеет выборочные ветки арта/PDF и frozen-plan runner,
но его хартия считает основным результатом принятый русский текстовый мастер;
сам перевод выполняется вне `prepare-translation`. По правилам NRI `translator`
остаётся legacy evidence. `Sourcefold` — отдельный проект с собственными
контрактами реконструкции/перевода/вычитки и пока не объявляет DOCX обязательным
результатом. Нужно отдельно решить, где будет жить новый продуктовый режим;
копировать старый код или переносить его требования автоматически нельзя.

## История, на которой надо оценивать универсальность

Первая инвентаризация `kb_creator` и `translator` обнаружила **восемь
различных исходных произведений**, а не только два последних. Это число
относится к двум обследованным контурам, а не ко всей истории NRI. Подробные
пути, стадии и оговорки о доступности байтов — в
[`A2-book-inventory.md`](plans/20260919-kb-creator-translator-flow-analysis/handoffs/A2-book-inventory.md).
Дополнительная проверка NRI Git и отдельного CoC publishing repo записана в
[`git-evidence.md`](plans/20260919-kb-creator-git-history-supplement/git-evidence.md).

| Произведение | Что доказывает для нового потока |
| --- | --- |
| The Innsmouth Terror | Сильный исторический пример полного PDF_EN→MinerU→RECONSTRUCTED_EN→accepted MASTER_EN/RU→HTML/PDF: 46 source pages, таблицы, статблоки, ассеты и много зафиксированных исправлений. DOCX в проверенных KB inputs и Git-истории не обнаружен. |
| Viral | Большой источник, MASTER_EN/RU и DOCX/HTML/PDF; публикация использует отдельный сценарный скрипт и не доказывает общий десятиэтапный маршрут. |
| Dissociation | Общий современный маршрут до DOCX/PDF и исправленного после пользовательской правки DOCX; релизное решение для итоговых байтов ещё открыто. |
| Number 7 Dream | Общий современный маршрут, ArtView, пользовательские правки DOCX и проверенный пакет; релизное решение ещё открыто. |
| Wormsign | Историческая Dune-ветка с полными EN/RU и HTML, документирован PDF; DOCX не подтверждён. |
| Desertflower | Generic Translator package с полными EN/RU, HTML и принятым PDF; DOCX не подтверждён. |
| Bless the Beast and Children | OCR-тяжёлый generic Translator package с полными EN/RU и принятым PDF по статусу; DOCX не подтверждён. |
| Mothers Love | Generic Translator example с материализованными EN/RU, HTML и PDF; статус принятия поздних файлов по этому анализу не установлен, DOCX не подтверждён. |

Innsmouth и Viral встречаются в обоих контурах и считаются по одному разу.
В более ранней NRI/CoC истории есть также `Innsmouth_Guide` (KB из уже русского
PDF), `Beyond_the_Edge_of_Darkness` и `Crawford_Inheritance` (сценарные
RU Keeper/HTML/PDF пакеты), Dune Corebook (большая PDF_EN→RU Markdown/HTML/PDF
локализация). `The_Lightless_Beacon`, `Memphis_House` и
`Edge_of_Darkness_1923` зафиксированы как intake/планы, поэтому завершёнными
прогонами не считаются. `The Innsmouth Terror` и `Innsmouth_Guide` — разные
проекты. Исторические публикации расширяют набор проверочных случаев, но
**не доказывают** единый воспроизводимый PDF_EN→DOCX_RU маршрут.

## Где накапливается лишняя сложность

- Нынешний публикационный граф всегда требует ArtView, принятого HTML, PDF и
  полного пакета даже тогда, когда нужен только редактируемый DOCX с ассетами.
- CLI реконструкции и CLI публикации — отдельные запуски; публикация продвигает
  не более одной стадии за вызов. `doctor` пока выдаёт только статус
  `ready_for_explicit_tool_preflight`, а не полный автоматический bootstrap.
- Скрипт `scenario_master_ru.py` готовит пакеты, проверяет и собирает
  представленный перевод, но не выполняет сам перевод и литературную вычитку.
- Изменение кода или конфигурации правильно инвалидирует старую identity,
  однако ручное создание нового run и перенос точных ранее принятых решений
  усложняют навигацию по версиям. В Number 7 Dream до сохранённого run30
  накопилось 29 исторических публикационных запусков.
- Часть дефектов относится к смысловому источнику: пропущенный текст, порядок
  чтения, тип таблицы/статблока должны исправляться до перевода. В DOCX
  переносятся решения оформления, а не восстановление утраченного содержания.

## Предлагаемый минимальный режим

`run --target docx` автоматически выполняет уже известные механические шаги,
останавливаясь только на неразрешённых содержательных вопросах. Внутренние
реконструкция, metadata, MASTER_EN/RU и QA остаются в run; выходной пакет
содержит точный проверенный DOCX, используемые ассеты и краткий manifest.
Полный ArtView, пользовательский HTML, финальный PDF, подробный публикационный
пакет и релизный review не входят в обязательный проход. Если рендерер пока
нуждается в HTML, он создаёт его как внутренний проверяемый промежуточный файл.
Пользовательская правка DOCX и последующий PDF — отдельный шаг того же
документированного процесса.
Если результат объявляется релизом, применяется отдельное независимое
релизное ревью по правилам NRI.

## Что ещё надо определить

1. **Статус DOCX после правок.** Предлагается принимать точный пользовательский
   DOCX как новую финальную authority текста и макета для PDF. `MASTER_RU`
   остаётся воспроизводимым текстом до постпродакшна; обязательная обратная
   ручная правка мастера противоречила бы цели упростить его. Нужен машинный
   отчёт о текстовых/структурных отличиях DOCX от мастера и явное правило для
   будущей пересборки, чтобы правки не исчезали незаметно.
2. **Порог для арта.** Нужны правила автоматической привязки из MinerU metadata
   к якорям и путь для спорных изображений. Отсутствие обязательного полного
   ArtView не должно скрывать нерешённые рисунки, карты и подписи.
3. **Точка готовности.** Минимальный результат — проверяемый DOCX + assets.
   PDF после пользовательской правки — отдельная опциональная финализация.
   HTML, читательский Markdown и большой evidence/release package — отдельные
   запрашиваемые выходы.
4. **Единый запуск.** Команда должна вести стадии до нужного результата,
   останавливаться на содержательных вопросах и продолжать тот же run с
   проверкой идентичности входов. Это должно убрать ручное управление версиями
   и последовательностью команд, сохранив исходные файлы и доказуемость.

## Ближайшая проверка гипотезы

Взять существующие принятые `MASTER_EN`/`MASTER_RU` и ассеты двух разных
сценариев, собрать DOCX по минимальному профилю без отдельного ArtView/HTML
acceptance и без обязательного PDF, затем сравнить полноту текста, иллюстраций,
таблиц и статблоков с уже просмотренными DOCX. Это пока предложение
эксперимента, не разрешение менять исторические пакеты или контракты.
`The Innsmouth Terror` стоит включить в первую пару: его принятые EN/RU,
таблицы, 22 карточки статблоков и ассеты дают строгий исторический эталон для
новой DOCX-проекции. Сравнивать следует полноту и структуру, а не равенство
страниц старого PDF: новое оформление иная издательская цель.
